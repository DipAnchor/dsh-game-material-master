# 渠道层与设置页改造方案

> 状态：**方案，尚未实现**。上一个增量（生成能力层 + 能力收敛）已经落地，
> 本文是它的下一步。动手前请先看完「7 未决问题」——那里有三条会影响取舍的硬约束。

## 0. 要解决什么

今天一个能力（生图 / 图生视频）只能配**一个**端点 + **一把** Key + **一个**模型，三者焊在一起：
`arkApiKey` 与 `arkBaseUrl` 是同一组扁平字段，而厂商又是写死的
（`engine/index.ts` 里 `IMAGE_INSTANCE_ID = "ark"`、`VIDEO_INSTANCE_ID = "minimax"`）。

于是「同一个端点换个账号」要连 URL 一起改，「两个账号」只能复制一份 URL，
「同一个端点放多个模型」没有位置——现有的 `arkRedrawModel` 就是为绕开这一点而生的补丁。

目标：把这三件事拆成三层，各自可配、可复用。

1. **供应商（账号）**：一把 API Key —— 只回答「用谁的 key」；
2. **渠道**：一个 API 地址 + **一个协议** + 一组模型 —— 只回答「打到哪、怎么说」；
3. **用途绑定**：生图默认 / 拆件 / 部件重绘 / 视频默认，各绑一个供应商
   （是否还要绑到具体模型，见 7.2 第 1 条）。

并且：新增第三家厂商时**不改调用方**（只加一个实例 + 一条渠道）；密钥**永不明文回到浏览器**。

## 1. 现状（要改掉的东西）

**宿主侧**

| 位置 | 现状 | 问题 |
|---|---|---|
| `config.ts` | `Config` 是扁平的单厂商字段：`arkBaseUrl/arkApiKey/arkModel/arkRedrawModel/arkSize/arkWatermark/arkTimeoutMs` + `minimax*` 一组 | 一个能力一个端点，装不下第二个渠道 |

| `config.ts:360-370` | `maskConfig` 是**闭合解构** `arkApiKey` / `minimaxApiKey`，其余 `...rest` 原样回传浏览器 | **新增任何密钥字段都会明文泄漏**（收进 `channelSecrets` 后此问题自然消失） |

## 2. 目标结构

三个层级，各自只管一件事：

| 层 | 是什么 | 键 | 只回答 |
|---|---|---|---|
| **供应商** supplier | 一把 API Key（一个账号） | `supplierId` | 用谁的 key |
| **渠道** channel | 一个 API 地址 + 协议 | `channelId` | 打到哪个端点、用哪套 wire |
| **模型** model | 端点上的一个 model / checkpoint | 渠道内 id | 用哪个模型（**使用时可选**） |

基数：

- 一个供应商 → **一个**渠道（`supplier.channelId` 是单值）
- 一个渠道 → **多个**模型（`channel.models[]`）
- 一个渠道 ← **多个**供应商（不同 key 可以指向同一个 apiurl）

也就是说 **key 与 url 解耦**。今天 `arkApiKey` 与 `arkBaseUrl` 是焊在一起的扁平字段，
于是「同一个方舟端点换一个账号」要连 URL 一起改、「两个账号」只能复制一份 URL。
这正是这次要修掉的。

**协议配在渠道上：一个端点一种说法。**

看 dsh-imagegen 渠道编辑器的实证（`SettingsCard.tsx:1402-1416`）：

| 字段 | 文案 | 值 |
|---|---|---|
| `channel.protocol` | 「接口协议」 | 自动检测 / Images API / Chat Completions |

**渠道上有且只有这一个协议字段**，而且它是**传输层**（走图像接口还是聊天接口）。
「哪家的 wire」（gpt-image / seedream / qwen / nanobanana）**不在编辑器里**——
它在 `model-catalog.ts:127-135` 由**模型 id 正则推**出来；推不出来就落到 `unknown`，
而界面文案是（`locales.ts:623`）：

> `channels.unknownProtocol`：**「未知协议，按通用 OpenAI 协议尝试」**

也就是说它的模型条目里只有 `{ alias, id }`，**没有协议字段**。`requestOneImage()`
（`engine.ts:735-820`）里那四行按 `params.model` 的分叉，是它在**猜这个端点该怎么说**，
不是在让用户配。

**所以我们的 `protocol` 放在渠道上**，值域是注册表里的协议 id
（`ark` / `minimax` / `gpt-image` / `qwen` / `comfyui` …），它 map 到一个
`ImageInstance` / `VideoInstance`。

> ⚠️ 同一个 UI 位置（都叫「接口协议」），**值域不同**：dsh-imagegen 的是**传输轴**
> （images / chat-completions），我们的是 **wire 族**。原因是我们**不猜**——
> 把它靠正则干的那件事显式化。代价是用户要选一次；好处是未知模型不会被静默按通用
> 协议发出去（它那句「未知协议，按通用 OpenAI 协议尝试」就是这个风险的自白）。
> 也因此我们**不需要**传输轴：真要支持聊天接口生图，再写一个适配器即可，
> 不必在渠道或模型上加第二根轴。

**为什么不是每个模型一个协议？** 因为协议描述的是「**这个端点怎么说话**」，
而一个端点只有一种说法——兼容网关也一样：它自己负责翻译，你把它标成「通用 OpenAI」
一次，它下面所有模型都走通用形状，没有理由逐模型标。

**同一端点真要两种说法** → **建两条渠道**（同 `baseUrl`、不同 `protocol`）。
我们的模型本来就允许：渠道 =「url + 协议 + 模型清单」，供应商再指向渠道。
等真遇到这个需求再加模型级覆盖，现在不加。

**模型条目是 `{ id, label? }`，不是 `{ id, protocol }`。**

- `id` 是**上游模型 id**，也是**身份**（任务快照、绑定、默认模型都记它）；
- `label` 是**可选的显示名**，只为界面好看；留空就用注册表目录里的标签，再退到 id 本身。

> dsh-imagegen 用 `{ alias, id }`，而且 **alias 才是身份**（`defaultModel` 存的是别名）。
> 我们反过来：**id 是身份、label 只是显示**。理由是别名可被用户随时改，让身份跟着改
> 会把存量任务快照和历史记录全部指错；显示名与身份分开就没有这个问题。
> 界面上要填的两个框是一样的。

### 2.1 三层怎么映射到调用

**解析顺序：先定模型 → 由模型反查渠道 → 由绑定定供应商。**

```
入参  { capability, purpose, model?, supplierId? }
 ① 定模型   model（本次执行）> 任务设置 > bind.model > 绑定供应商渠道的第一个模型
 ② 定渠道   反查「哪个渠道承载这个模型」——模型决定渠道，不是渠道决定模型
 ③ 定供应商 supplierId > 任务设置 > bind.supplierId > 指向该渠道的第一个供应商
 ④ 取密钥   channelSecrets[供应商]
 ⑤ 组装     InstanceContext { protocol, baseUrl, apiKey, model, timeoutMs, options }
```

**为什么是「模型 → 渠道」而不是反过来？** 因为**每一次执行都可以用不同模型**——
一个任务的多张图、一个项目的八个方向、一个骨骼的十几个部件，各次执行彼此独立，
用户完全可以在某一次换模型重试。既然如此，模型就是**每次调用**的参数，
而渠道只是「这个模型在哪」的结果。

**这与 dsh-imagegen 完全一致。** 它的 `GenerateRequest` 里就带 `model`（`protocol.ts` 原文）：

> *User-facing model name (an alias from the channel's model catalog). The host maps it onto
> the configured channel and fills `upstream` with the real id before the engine sees it.*

而 `resolveChannelRequest()`（`routes.ts:556-581`）干的就是反查：

```ts
const target  = channels.find(c => c.id === request.channelId) ?? defaultChannel  // 可选锚点
const asked   = request.model.trim()
if (asked === '') { /* 用 target 的第一个模型 */ }
const hosting = channels.filter(c => c.models.some(m => m.alias === asked))       // ← 反查
if (hosting.length === 0) { /* 报错：模型未在任一渠道配置，并列出可用模型 */ }
const picked  = target?.models.some(m => m.alias === asked) ? target : hosting[0]
// 再把 request 补全成 { model, upstream: mapping.id, channelId, channel }
```

注意两点：**`model` 是请求参数**（每次调用各带各的），**`channelId` 只是可选锚点**
（优先用它，但它不含这个模型时就换成真正承载它的那条渠道）。

`InstanceContext` 的字段来源：

| `InstanceContext` 字段 | 来自 |
|---|---|
| `model` | 本次执行 > 任务设置 > `bind.model` > 渠道第一个 |
| `protocol` | **渠道**（由模型反查出来的那一条） |
| `baseUrl` | 渠道 |
| `options`（尺寸 / 去水印 / 路径前缀…） | 渠道 |
| `apiKey` | 供应商（经 `channelSecrets[supplierId]`） |
| `timeoutMs` | 渠道 `options`（缺省回落到全局 `arkTimeoutMs` / `minimaxTimeoutMs`） |

**协议为什么在上下文里？** 除了取适配器（`imageInstance(protocol)`），还有两个用处：

1. 适配器**内部还有方言**时要照它走：`minimax.ts` 按模型分 v1 / v2，
   `engine.ts:801` 按 `isVolcSeedream` 分 `url` / `b64_json`；
2. **让任务快照记全「这次调用用的哪套 wire」**，事后可复现。

> 第 2 点正好解掉一个现存妥协：`seqgen.ts:418-422` 的注释写着「任务的模型快照一旦和当前
> 网关对不上就会打出 404，所以以全局配置为准、忽略任务快照」。拆开之后，快照里记的是
> `supplierId` / `model` / `protocol`，三者同源、天然配套，那条妥协可以退役——
> **而且任务表单本来就该能自己选模型**（见 4.5：四个模块早就有 `settings.model`）。

所以 **engine 那一层几乎不用改**——变的只是「上下文从哪来」。

### 2.2 密钥仍然单独存，但**键是供应商**

`channelSecrets[<supplierId>]`——因为 key 是供应商的属性。这也让「同一渠道多个供应商」
天然各持一把 key，互不干扰。

两条理由：

1. 任何一次**整对象写回**都会覆盖没重填的字段；密钥单独一层后，供应商对象里根本没有 secret。
2. 这样 `maskConfig` 不必再维护白名单——回传浏览器天然安全。

> 命名提醒：「供应商」在中文里和「厂商」太像，容易和渠道上的 `protocol` 混。
> 代码里请用 **`supplier`**（账号 / 凭证）与 **`protocol`**（说话方式）两个词，
> 文档里写「供应商（账号）」与「协议」。


## 3. 宿主侧改动（**必须先做，界面改不动它**）

### 3.1 配置结构（`config.ts`）

新增三组类型与 `DEFAULT_CONFIG` 初值：

- `ChannelConfig { protocol, name, baseUrl, models: ModelEntry[], options? }`
- `ModelEntry { id: string, label?: string }` ← **模型条目只有上游 id 与可选显示名**
- `SupplierConfig { name, channelId }`
- `BindConfig { image: { default, sheet, redraw }, video: { default } }`
- `BindSlot { supplierId: string, model?: string }` ← `model` 缺省＝渠道第一个模型

`normalizeConfig` 负责收敛：id 用 `[a-z0-9-]{1,40}`；渠道的 `protocol` 不在注册表里则
**整条丢弃**并记警告——协议决定整条渠道的请求形状，与其留着让它发错、不如丢掉；
渠道的 `baseUrl` 为空或 `models` 为空也丢弃；供应商的 `channelId` 指向不存在的渠道则
丢弃该供应商；`bind` 指向不存在的供应商则回落到第一个可用项。

`ark*` / `minimax*` 扁平字段**暂时保留**：它们是迁移的来源，也是其他界面位置的依赖（见 4.6）。

### 3.2 新增/删除的 RPC

嵌套对象进不来现在这种 patch：`saveConfig` 是**白名单 patch**（`index.ts:248-281` 的 `directKeys`），
不在名单里的键根本传不到保存；而一旦把 `channels` 加进名单，它就是**整体替换**——所以必须有逐渠道
RPC（详见 9.1 ①）。新增方法（`wire.ts` 的 `METHODS` 要同步）：

| 方法 | 作用 |
|---|---|
| `saveChannel({ id?, protocol, name, baseUrl, models, options })` | `id` 缺省＝新建，否则更新（**不碰任何密钥**）。`models` 是 `[{ id, label? }]` |
| `deleteChannel({ id })` | 若仍有供应商指向它则**拒绝**，并列出是哪几个 |
| `saveSupplier({ id?, name, channelId })` | 新建 / 改名 / 换渠道 |
| `deleteSupplier({ id })` | 若仍被 `bind` 引用则拒绝，并列出是哪些用途 |
| `saveSupplierKey({ id, apiKey })` | 只在该供应商上写密钥；空串＝清除 |
| `bindSupplier({ capability, purpose, supplierId, model? })` | 改一条绑定（`model` 省略＝用渠道第一个模型） |
| `testSupplier({ id })` | 用「该供应商 + 其渠道 + 渠道第一个模型」跑一次连通性自检 |

`testArk` / `testMinimax` 由 `testSupplier` 取代；两者在 `wire.ts`、`client.ts` 的 `REMOTE_METHODS`
与 `api` 对象、以及 `verify-host` 里都出现，需要一起改。

> 「测试连接」测的是**供应商**而不是渠道——一次真实调用必须有 key，只有渠道测不了。

**另外：所有生成类方法都要多一个可选 `model`（以及可选的 `supplierId`）。**

这是「每一次执行都能换模型」的落点（见 2.1 与 4.5）。全部生成类方法：
`runImage` / `runImages` / `runVideos` / `runTurnVideo` / `runFrames` / `compose`、
`runImageJob` / `runSequenceVideo` / `runSequenceFrames` / `composeSequence`、
`runRigSheet` / `runRigRedraw` / `runRigLayout` / `runRigBones` / `runRigAtlas`。

其中**真正花钱**的是这几个，它们的 `model?` 最有价值：
`runImage`、`runImages`、`runVideos`、`runTurnVideo`、`runImageJob`、
`runSequenceVideo`、`runRigSheet`、`runRigRedraw`。
两个特别值得注意：

- `runImage({ projectId, key })` 是**逐方向**的 → 「这个方向换个模型重来」；
- `runRigRedraw({ jobId, name, prompt })` 是**逐部件**的 → 「这个部件换个模型重画」。

### 3.3 密钥与脱敏

- 删掉 `maskConfig` 里对两个 key 的解构：供应商对象与渠道对象里都**不含**密钥，直接回传；
- 密钥只以 `{ keySet: boolean, keyHint: string }` 的形式挂在**供应商**上（沿用现在
  `arkApiKeySet` / `arkApiKeyHint` 的做法，含「≤8 位显示已配置」那条规则）；
- `channelSecrets` 永不出现在视图里。

### 3.4 迁移（一次性，幂等）

读配置时若 `channels` 为空而旧的扁平字段有值：

1. 用 `arkBaseUrl` 建渠道 `ark-cn`（`protocol: "ark"`）：`models` = `[{ id: arkModel }]`
   （`arkRedrawModel` 非空且不同则一并追加），
   `options` = `{ size: arkSize, watermark: arkWatermark }`；
2. 用 `minimaxBaseUrl` 建渠道 `mm-intl`（`protocol: "minimax"`）：`models` = `[{ id: minimaxModel }]`，
   `options` = `{ duration, resolution, pathPrefix }`；
3. 建供应商 `ark-main`（→ `ark-cn`）与 `mm-main`（→ `mm-intl`），把两把 Key 搬进 `channelSecrets`；
4. `bind.image` = `{ default: { supplierId: "ark-main" }, sheet: { supplierId: "ark-main" },
   redraw: { supplierId: "ark-main" } }`，`bind.video` = `{ default: { supplierId: "mm-main" } }`；
   **若 `arkRedrawModel` 非空**，额外建供应商 `ark-redraw`（同样指向 `ark-cn`）并绑到 `redraw`
   且带上 `model: arkRedrawModel`——这正是「同一渠道、两个用途、各自一把 key 与模型」的用法，
   也是三层模型相对旧结构的直接好处；
5. 写 `migration.channels = 1` 标记，避免重复迁移。

旧字段**不删除**（回滚与排错都要）。

> `capabilities`（复数）与 `defaults: { baseUrl, models }`。实现时拆成了
> `capability`（单数，该协议属于哪个能力面）、`defaultBaseUrl`、`hosts`、`presets`、
> `probeable`——同样的信息，但少了「`defaults` 里塞一个数组又塞一个字符串」那种含糊，
> 而且「能不能检测」这件事原本无处安放。另外补了两处：
> - `channels[].models[].capability`——§4.7 的能力驱动控件靠它决定**渲染哪些控件**，
>   协议不支持就不渲染，不留「填了但没用」的输入框；
> - `resolved`——每条用途绑定**解析后**实际走哪条渠道的哪个模型。界面靠它显示
>   「现在到底用的是哪条渠道」，验收脚本靠它断言四级回落与模型反查渠道（§2.1）。
>   它只是把 `resolveTarget` 跑一遍给人看，不参与任何生成。

- `channels[].protocol` + `protocolLabel`——协议在**渠道**上，是「接口协议」下拉的当前值；
- `channels[].models[]` 每条只有 `id`、`label` 与 `capability`（`label` 缺省由协议注册表里的
  catalog 补，未知 id 就显示 id 本身）——这就是「一个渠道可以包含多个模型」的落点；
- `protocols` 是**可选协议清单**（来自 `engine/registry.ts` 的 `listImageInstances()` /
  `listVideoInstances()`），供「接口协议」下拉使用并预填地址与内置模型目录；`capability` 说明该协议
  属于哪个能力面（生图 / 图生视频），界面据此过滤（例如视频渠道里不列 `ark`）；
- `suppliers[].keySet` / `keyHint` 是密钥的全部对外信息。

### 3.6 实例 id 不再写死

**已按此实现（U1）**，两处与原文的不同：

- `imageEngine` / `videoEngine` 吃的是**解析结果**（`ResolvedTarget = { protocol, context,
  supplierId, channelId }`），不是 `(config, { capability, purpose, model?, supplierId? })`
  ——把「解析」与「绑定实例」拆开之后，轮询那种要跨进程重建上下文的路径才能复用同一个解析器；
- `InstanceContext` **没有**加 `protocol` 字段。原文假设适配器需要它，但现有两个适配器都
  不需要（`minimax.ts` 的 v1/v2 由模型 id 自己推）。等第一个需要「同一实例服务两种协议」
  的适配器落地时再加——现在加只是多一个没人读的字段。


## 4. 界面侧改动（`src/client.ts`）

**这一节按 dsh-imagegen 的真实交互形态写**（入口、字段顺序、文案、模型目录的双路径、
生图时的分组选择），再叠加我们比它多的两块：**供应商**与**用途绑定**。

### 4.1 设置页新结构

现有两个分组（「火山方舟（生图）」「MiniMax（图生视频）」）换成五块：

1. **渠道**——列表 + 「添加提供方」/「添加自定义渠道」；每行：协议标签 · 名称 · Base URL ·
   模型数 · 编辑 · 删除。顶部一句摘要（它的是「{channels} 个渠道 · {models} 个模型」）。
2. **供应商**——列表 + 「新增供应商」；每行：名称 · 指向的渠道 · 密钥状态 · 测试 · 编辑 · 删除。
3. **用途绑定**——四行下拉：生图默认 / 拆件 / 部件重绘 / 视频默认。
4. **默认生图模型**——一个**按渠道分组**的下拉（见 4.5）。
5. **新建项目的默认参数** 与 **数据位置**——保持不动。

**供应商是 dsh-imagegen 没有的一层**（它的 key 直接挂在渠道上），**用途绑定也是我们没有的增量**。

### 4.1.1 外壳：照它的形态做（原文漏了，后来返工补上）

上面那一节只规定了**内容**（五块、字段顺序、模型目录的两条路），**没规定外壳**。结果是
第一版做成了一屏平铺五个分组、全部展开、改一下就保存——和 dsh-imagegen 摆在一起看
完全不是一回事，用户一眼就指出了。补上：

| 元素 | 形态 |
|---|---|
| 顶部 | 一句总状态：「先添加一条渠道开始使用」/「都已配好，可以直接开始」 |
| **配置概览** | 2 列状态卡（渠道与模型 / 供应商与密钥 / 用途绑定 / 生成环境 / 数据位置），需要关注的那些描边高亮，**点卡片或分组标题展开对应分组** |
| **手风琴分组** | 标题 + **一行**短说明 + 右侧状态 pill + chevron；**每次只展开一个区域** |
| 组内入口 | 统一 `+ ` 前缀：「+ 添加提供方」「+ 添加自定义渠道」「+ 新增供应商」 |
| 列表行 | 一行的**名称（加粗）+ 次要信息**两层，右侧留操作按钮 |

折叠用 CSS（`.SPR_settingsGroup.SPR_collapsed > *:not(.SPR_sectionHead){display:none}`），
**不条件渲染**：分组体是几百行 JSX，与折叠无关，为加外壳去动它风险大收益小。

> ⚠️ 与它的一处**有意不同**：它底部是「放弃修改 / 保存」（草稿语义）。我们的渠道 / 供应商
> 各自是独立的 CRUD 调用，保存即生效、没有草稿可放弃，所以不放那个底栏，改成顶部写明
> 「改动即时生效，不需要点保存」。**这是唯一有意偏离的地方**，其余照抄。

### 4.2 添加渠道：先选提供方

它的入口是「添加提供方」而不是空白表单（`channels.addProvider` / `channels.addCustom`）：

- **添加提供方**：列出内置目录（我们的 `protocols`，见 3.5），点一个就预填 `baseUrl` +
  模型清单 + 协议，用户基本只填 API Key；
- **添加自定义渠道**：空白起步，协议自己选。

它的目录里还分「API Key」/「订阅账号」两类（`channels.presetTabApiKey` /
`presetTabSubscription`）。我们**没有订阅体系，第二类不做**——但目录结构留着，以后要加不用改形状。

### 4.3 渠道编辑器

就地展开（与现有 `SPR_settingsGroup` 风格一致），字段与它一一对应：

| 顺序 | 字段 | dsh-imagegen 对应 |
|---|---|---|
| 1 | 显示名称 | `channels.displayName`「显示名称」 |
| 2 | **接口协议**（下拉：注册表里的协议 id） | `channels.protocol`「接口协议」 |
| 3 | Base URL | `channels.apiUrl`「API 地址」 |
| 4 | **模型目录** | `channels.modelCatalogTitle`「模型目录」 |
| 5 | 渠道参数 `options` | 它没有——这是我们已有的尺寸 / 去水印 / 时长 / 分辨率 |

⚠️ **没有 API Key**——密钥在供应商那一块。这是最容易做错的一处：今天 Key 与 Base URL
躺在同一个分组里，迁移时很容易顺手把 Key 留在渠道表单上。

> 它的「接口协议」值域是**传输轴**（自动检测 / Images API / Chat Completions），我们的是
> **wire 族**（`ark` / `minimax` / `gpt-image` / `comfyui` …）。**同一个位置、不同值域**，
> 理由见 §2。它那个「完整 URL」开关我们**不需要**——那开关是用来「跳过族路由、改走通用
> OpenAI 形状」的，而我们本来就是显式选协议。

### 4.4 模型目录：检测 + 手动两条路

这是它做得最顺的一处，照搬。它自己那句话把两条路说全了（`channels.noModelsHint`）：

> 「暂无模型：点击**检测**拉取候选，或手动添加；别名（显示名）默认等于上游模型 id，可自行修改。」

- **检测**：`channels.detectFirst`「检测模型」/ `channels.detect`「重新检测」/
  `channels.detecting`「检测中…」，完成后回执 `channels.detectSuccess`「连通 ✓ · {n} 个候选」。
  它那条自动触发条件值得照抄（`SettingsCard.tsx:1278`）：**URL 与密钥都就绪时才自动跑一次**，
  之后交给手动。
  - 宿主侧照它 `prompt-enhancer.ts` 的做法：按 baseUrl 拼 `/models`（`…/chat/completions`
    结尾时回退到上一级再拼），拉回后筛出像生图模型的候选；
  - **筛选我们可以比它准**：它用 `isLikelyImageModelId` 正则猜，我们有协议注册表，
    可以按「该协议的已知模型前缀」判断。
- **候选点选**：`channels.candidatesTitle`「图片模型候选（点击加入）」。
- **手动添加**：`channels.manualAddPlaceholder`「输入模型 id，例如 qwen-image」+ 添加。
- **每行两个框**（对应它的 `channels.modelAliasLabel` + `channels.modelIdLabel`）：
  **上游模型 id**（必填，身份）与**显示名**（选填，留空用目录标签）。
- 几个小细节也照抄：`channels.copyFrom`「从其他渠道复制…」、`channels.modelCount`
  「{n} 个模型」/ `channels.noModels`「未配置模型」；删除确认里它会写明「该渠道的密钥将被移除」，
  **我们这里密钥属于供应商，措辞要跟着改**。

### 4.5 模型选择：**每一次执行都能选**，其余都只是默认值

这一处我写错过两次，一并说清：

- 第一次我断言八方向图 / 序列帧 / 骨骼动画「没有逐次交互的位置，只读 `bind`」。
  **位置一直都有**——四个模块本来就有持久化的 `settings.model`。
- 第二次我把粒度定在「任务」上（表单设一次、任务内固定）。**还是粗了**：
  一个任务的**每一次执行**都可以换模型。

**真正的粒度是「每次执行」。** 而且 dsh-imagegen 就是这样：`GenerateRequest` 自带 `model`
（`protocol.ts` 原文：*User-facing model name… The host maps it onto the configured channel*），
每次生成各带各的；`defaultModel` 只是没指定时的兜底。表单与 `bind` 同理，都只是**默认值**。

**四级优先级**：

| 级别 | 在哪 | 例子 |
|---|---|---|
| ① 本次执行 | 生成类 RPC 的 `model` 参数 | 「这张不满意，换 4.5 再来一次」 |
| ② 任务 / 项目设置 | `settings.model`（**已存在**） | 这个项目默认用 4.5 |
| ③ 用途绑定 | `bind[能力][用途].model` | 重绘默认用 4.5 |
| ④ 渠道第一个模型 | `channel.models[0]` | 什么都没配时的兜底 |

**为什么必须到「每次执行」这一级**——这不是理论推演，现有代码里已经就是这个形态：

- `runImage({ projectId, key })` 是**逐方向**的 → 重跑一个方向当然该能换模型；
- `runRigRedraw({ jobId, name, prompt })` 是**逐部件**的 → 「这个部件换个模型重画」天然成立；
- 图片生成的任务有 `items[]`，`runImageJob({ jobId, count })` 可以反复跑——换模型再跑一批
  是常见操作。

**证据：字段已在，覆盖点连注释都是现成的。**

| 模块 | 读回（已持久化） | 现在执行时覆盖 | 覆盖处给的理由（原文） |
|---|---|---|---|
| 图片生成 | `imagegen.ts:217` | `imagegen.ts:280` | 「生图模型同样是全局设置，任务只跟随、不覆盖」 |
| 八方向图 | — | `index.ts:851` | 「任务里不保留可覆盖的副本」 |
| 序列帧 | `seqgen.ts:283` | `seqgen.ts:422` | 「任务的模型快照一旦和当前网关/Key 对不上…就会打出 404」 |
| 骨骼动画 | `riggen.ts:788` | `riggen.ts:2926` | 直接覆盖；`index.ts:960` 连时长/分辨率一起收敛 |

**这些理由全都是扁平配置的产物**：模型、Key、网关原本只有一个全局槽位，任务快照擅自改
其中一个就会错配。渠道层之后它们同时消失：

- 模型 + 协议 + `baseUrl` 来自**同一条渠道** → 天然配套，不会出现「官方 H3 + 优云智算网关」；
- 「存下当前模型不支持的档位」→ 档位改为**从该渠道协议的 capability 收敛**，就是 4.7 那件事。

**下拉本身照抄 dsh-imagegen**：`settings-scope.ts:324-329` 按渠道成组（**默认渠道排第一**），
`SettingsCard.tsx:662` 用 `<optgroup label={group.name}>` 渲染——所谓「分组」是**字面意义上的
`<optgroup>`**，组名是渠道名，组内是模型的显示名。它是**同一个控件的两个挂载点**：
设置页里是默认值，生成界面里是本次执行的值。

**表单 / 任务设置里仍要显示**（作为默认值与当前值），按模块实际用到的用途各给一行：

| 模块 | 表单里的模型行 | 对应 `bind` |
|---|---|---|
| 图片生成 | 生图模型 | `image.default` |
| 八方向图 | 生图模型 · 视频模型 | `image.default` · `video.default` |
| 序列帧 | 视频模型 | `video.default` |
| 骨骼动画 | 拆件模型 · 重绘模型 | `image.sheet` · `image.redraw` |

落到代码是四处：`client.ts:3812` `GlobalModelField`（现在读 `globalConfig?.arkModel`）改成这个
分组下拉、`client.ts:7559` 骨骼动画的模型徽标同理、各模块表单新增上表那几行、
**生成按钮旁也挂一个**（本次执行）；上表「现在执行时覆盖」那**五个覆盖点**改成
「读本次入参 → 任务设置 → `bind`」的逐级回落。

### 4.6 供应商编辑器与密钥交互

供应商编辑器只有三项：名称、指向哪个渠道、API Key。

密钥沿用现有约定，只是从两个固定 key 变成**每供应商一个**：不带就是保持原值，带空串才是清除，
界面永远拿不到明文。它的几处措辞可以照抄：「已配置 — 输入新值可替换」、「清除密钥」、
「显示 / 隐藏密钥」，以及列表里的「密钥已设置 / 未设置密钥」。

> ⚠️ 更正：「`verify-client` 有一条密钥契约扫描」是我编的——**`verify-client.mjs` 里没有任何
> 密钥脱敏断言**。它真正管的是 `FEEDBACK_REQUIRED`（`:149-174`）那条「`{ key, label }` 必须是
> 最后一个实参」的契约，而那条契约会影响本次改造（`model` 不能做成位置参数，见 9.1 ③）。

**「换渠道」是一等操作**（供应商与渠道是多对一）：改 `channelId` 即可，密钥不动
——这正是 key 与 url 解耦之后才做得到的事。

### 4.7 能力驱动控件

现有实现读 `config.minimaxCapabilitiesByModel[config.minimaxModel]`（8048-8055）。
改为读**该渠道协议**的 capability：

- 时长：`durations`（定值档）或 `durationMin`~`durationMax`（区间）
- 分辨率：`resolutions`
- 生图尺寸：`sizes`

好处是「填了但没用」的控件会消失——协议不支持就不渲染。

### 4.8 优云智算怎么处理

现在靠 `onModelChange` 联动改 Base URL（8057-8070）+ `videoGatewayVariant()` 桥。在渠道模型下
它应该变成一个**预设渠道**（baseUrl 预填 `https://cp.compshare.cn`，模型仍是 `MiniMax-H3`）。

⚠️ **但这一步做不到**：`minimax.ts` 的 `gatewayOf()` 在模型 id 命中 `COMP_SHARE_MODEL_ID` 时
**忽略传入的 baseUrl**（`minimax.ts:155-157`），`pathPrefixOf()` 同理加 `/minimax`。
也就是说渠道里填的地址对优云智算不起作用。

**已决（见 7.1 ②）**：U2–U3 先不动它——「优云智算」保留为渠道编辑器里的一个预设开关，
继续走 `gatewayVariant()`；让渠道地址优先的改造作为**独立的 P6**，
连同它自己的迁移与 `verify-minimax` 改写一起做。

### 4.9 其他引用了扁平字段的界面位置

这两处**不在设置页里**，容易漏：

- `client.ts:3812` `GlobalModelField`（图片生成模块里显示「生图模型」）读 `globalConfig?.arkModel`
- `client.ts:7559` 骨骼动画的模型徽标读 `globalConfig?.arkModel`

4.5 的分组下拉落地后，它们改成读该下拉的值，扁平字段才能从视图里彻底删掉。

## 5. 硬约束（改界面时必须守）

| 约束 | 说明 |
|---|---|

## 7. 决策记录与未决问题

### 7.1 已决

**① `ark.ts` / `minimax.ts` 本批**保持字节不动**。**

渠道层**不修改**这两个模块，实例继续做薄包装。理由：

- 它们是**受测契约**：`verify-minimax.mjs` 有 85 项直接打这两个模块（`capabilityOf` / `normalizeDuration` / `pathPrefixOf` / `gatewayOf` …），`verify-host` 又跑通了宿主全链路。重写零收益、纯风险。
- 我们一路守着的「改结构不改行为」靠的就是这条隔离：P0 那次大改能拿到 875 项全绿，正是因为厂商代码一个字节没动。渠道层是同等级别的结构改动，继续隔离才能把失败面框住。
- 真正需要改的只有一处（见 ②），而它是**行为相邻**的改动，理应单独走一遍迁移与自检。

**② 唯一例外：优云智算的硬编码网关——要改，但单独作为一个改动，不混进渠道层。**

`minimax.ts` 的 `gatewayOf()` 在模型 id 命中 `COMP_SHARE_MODEL_ID` 时**忽略传入的 baseUrl**，`pathPrefixOf()` 同理加 `/minimax`（`minimax.ts:145-167`）。这是「一个模型 id 代表一个渠道」的历史遗留——作者当时只有**一个**扁平端点槽位、没有第二个渠道可用，只能把网关编进模型 id。渠道层落地后这个理由就消失了，它应该退化成**预设渠道**（模型仍是 `MiniMax-H3`，baseUrl 指向 `https://cp.compshare.cn`，路径前缀 `/minimax` 从渠道参数来）。

之所以**不并进这一批**：

- 它会改变「某个已存的模型 id 实际打到哪个地址」，属于**行为改动**，需要自己的迁移（把存量的 `MiniMax-H3 优云智算` 映射成预设渠道）；
- `verify-minimax.mjs` 里直接测 `gatewayOf` / `pathPrefixOf` / `isCompshareModel` / `COMP_SHARE_*` 的那几项要改写，这是**验收门本身的变化**；和渠道层混在一起会让两件事都难定位。

**因此 U1–U3 期间**：渠道的 `baseUrl` 对优云智算那个模型 id 是**冗余字段**（填了不生效，但预设填进去的值就是正确值，所以实际不会出错）。代价是 `videoGatewayVariant()` 这个桥暂时留着，P6 时删掉。

> 渠道 schema **不需要为 P6 预留什么**：`options` 本来就是自由字典，P6 落地时把 `pathPrefix` 放进去即可。

**③ 存量配置字段：兼容，分两步退场。**

`ark*` / `minimax*` 扁平字段**保留**，读配置时迁移成渠道与供应商（3.4 节），U1 期间
**继续原样输出到视图**——所以设置页一行都不用改，行为与今天完全一致。到 U4 再删，
前置条件是改掉 4.6 节那两处界面引用（`client.ts:3812`、`7559`）。

`arkRedrawModel` 同样处理：非空时**额外建一个供应商** `ark-redraw`（指向同一个渠道
`ark-cn`）并绑到 `redraw`；字段本身留到 U4 再删。

**④ 一个渠道多个模型（推翻我在附录 A2③ 的建议）。**

附录里我建议「先保持一渠道一模型」。按你的定义改为：**渠道带 `models: string[]`，
模型在使用时可选**。

好处是同一份 key + 同一个端点下可以摆多个模型（Seedream 4.0 / 4.5 / 5.0），按用途或按
需要挑，不必为每个模型复制一条渠道——旧的 `arkRedrawModel` 之所以存在，正是因为当时
没有「渠道多模型」这个位置。

代价是 `bind` 的语义要多一层：只绑到供应商还不够，还得知道用哪个模型。见 7.2 第 1 条。

**⑤ 三层之间的关系（按你的定义固化）。**

```
供应商(apikey) ──N:1──▶ 渠道(apiurl) ──1:N──▶ 模型
```

- `supplier.channelId` 是单值：一个账号只属于一个端点；
- 同一个渠道可以被多个供应商指向（同一端点、多把 key）；
- 渠道的 `models[]` 是该端点可用的模型清单，每条是 `{ id, label? }`。

`channels` / `suppliers` 放顶层；能力归属由**渠道的 `protocol`** 决定；只有 `bind` 按能力分。

**⑥ 协议的位置：配在渠道上；而它进 `InstanceContext`。**（本方案改过三轮，这里记最终结论）

这一条来回改了三次，三次都留在这里，因为中间两次错得很有代表性：

- **第一轮**：字段叫 `instance`、放在渠道上，当成「选厂商」。错在**名字**——
  dsh-imagegen 自己把这一层叫**协议**（`model-catalog.ts:135` 的 `unknown` 家族，
  界面标签直接写「未知协议」）。
- **第二轮**：名字改对了（`protocol`），但断言改成「上下文不带协议，因为协议是选适配器的入参」。
  错在**层级**——我把它的 `channel.protocol`（`images` / `chat-completions`）说成
  「适配器的子协议」，方向反了；那是**传输轴**，而且优先级更高。
- **第三轮**：看到 `requestOneImage()`（`engine.ts:735-820`）里并排四个按 `params.model`
  分叉的协议分支，我读成「协议是模型的属性 → 所以每个模型配一个协议」。
  **这是过度外推**：那些分支是它在**猜这个端点该怎么说**，不是让用户逐模型配。

**最终结论：**

- `protocol` 配在**渠道**上——协议描述的是「**这个端点怎么说话**」，而一个端点只有一种说法。
  `models` 只是 `{ id, label? }`，**添加模型时不出现协议**。这正是 dsh-imagegen 的形态：
  它的模型条目只有 `{ alias, id }`，渠道编辑器里 `protocol` 只出现一次
  （`SettingsCard.tsx:1402`）。
- `InstanceContext.protocol` **保留**，装**这次调用生效的协议**（取自渠道）。它有两个用处：
  适配器内部还有方言时（`minimax.ts` 的 v1 / v2、`isVolcSeedream` 的 `url` / `b64_json`）
  要照它走；以及让任务快照记全「这次调用用的哪套 wire」。
- 同一端点真要两种说法 → **建两条渠道**（同 `baseUrl`、不同 `protocol`）。
  我们的模型本来就允许。等真遇到再加模型级覆盖，现在不加。

**它怎么解决「同一端点混族」？靠猜，外加一个逃生舱。** 它没有任何逐模型的协议配置，
靠 `describeModel()` 的正则把 `gpt-image` / `seedream` / `qwen` … 认出来；认不出就落到
`unknown`，界面文案就是那句自白（`locales.ts:623`）：**「未知协议，按通用 OpenAI 协议尝试」**。
另加 `apiUrlFull: true` 作为第二条路——「我给了完整 URL，你别猜、也别再拼路径」。
我们把这个「猜」换成**渠道上显式选一次**：代价是要选一次，好处是未知模型不会被静默
按通用协议发出去。

**关于那根传输轴**（`images` / `chat-completions`）：它确实存在，且**优先级高于协议**
（`engine.ts:1197` 先判它，命中 chat 就直接返回）。但我们**不需要**它——
它之所以在 dsh-imagegen 里必须存在，是因为那里 dispatch 是一条 if 链，`chat-completions`
必须在链首短路。我们的 engine 是适配器 + 注册表：真要支持聊天接口生图，
**再写一个适配器**即可（例如 `openai-chat`），不必在渠道或模型上加轴。

**⑦ 模型是「每次执行」的参数；解析顺序是「模型 → 渠道 → 供应商」。**

- `model` 是**生成类方法的可选入参**，不是任务的固定设置——`runImage` 逐方向、
  `runRigRedraw` 逐部件、`runImageJob` 可反复跑，每一次都能换。
- **四级优先级**：本次执行 > 任务设置 > `bind.model` > 渠道第一个模型。
- **渠道由模型反查**（dsh-imagegen 的 `resolveChannelRequest()` 就是这么做的），
  而不是先定渠道再挑模型。所以解析顺序与直觉上的「渠道 → 模型」相反，见 2.1。
- `bind` 因此降为**默认值**：`{ supplierId, model? }`。
- 代价：生成类方法（`wire.ts` 的 `METHODS`、`client.ts` 的 `REMOTE_METHODS` 与 `api` 对象、
  `verify-tools` / `verify-host`）都要多一个可选 `model`，见 3.2。

**⑧ U1 的真源规则：扁平字段与各自绑定的默认渠道互为投影（方案 A）。**

我审计时发现 U1 有个没定死的语义：旧设置页**只写扁平字段**，而 `saveConfig` 的白名单里
没有 `channels`——若按「渠道是真源」写，旧页面的改动就到不了渠道，看着生效其实没生效。

已定：**U1 期间两个方向都投影**——`saveConfig` 写完扁平后重算默认渠道/供应商；
新 RPC 写完渠道后投影回扁平。完整规则、触发点与四条不变量见 **9.4**，那是 U1 的验收依据。

## 9. 落地清单：审计发现的遗漏与更正

### 9.1 三处措辞/事实要更正

**① `saveConfig` 的两段机制要分开说清（§1 那张表其实已经写对了）。**

它先是**白名单**（决定「什么键能进来」），落盘时才是**浅合并**（`{...current, ...patch}`）。

真实形状（`index.ts:245-293`）：

```ts
const patch: any = {};
const directKeys = [...];                          // 248-277 的白名单
for (const key of directKeys) if (input[key] !== undefined) patch[key] = input[key];   // 278-281
if (typeof input.arkApiKey === "string") patch.arkApiKey = input.arkApiKey.trim();     // 282-285
if (input.clearArkApiKey === true) patch.arkApiKey = "";                               // 286-289
const saved = await saveConfig(patch);                                                 // 290
```

而 `config.ts:317-325` 的 `saveConfig` 是**浅合并 + 归一化**：
`normalizeConfig({ ...current, ...patch })`。

结论不变（整对象写回会覆盖），但**理由要写对**：`channels` 不在白名单里进不来；
一旦加进白名单，它就是**整体替换**，所以必须有逐渠道 RPC。密钥那两个特例（带 `arkApiKey`＝改、
带 `clearArkApiKey`＝清、都不带＝保持）是 `saveSupplierKey` 要照抄的语义。

**② `verify-host` 的配置断言块是 174-260，不是 192-215。**

起点在 `verify-host.mjs:177`：`check("默认使用 Seedream 4.0", initial.arkModel === "doubao-seedream-4-0-250828", …)`；
末尾还有 `218`（`saved.arkApiKeySet === true`）、`248`（「不带 Key 的保存不会清空 Key」）、
`250`（「clearArkApiKey 能清空 Key」）。全块共 **22 处**命中 8 个视图字段。

**③ 「`verify-client` 有一条密钥契约扫描」——不存在。**

`verify-client.mjs` 里没有任何 `arkApiKey` / 脱敏相关断言。它真正管的是**另一件事**，而且那件事
会直接影响本次改造：`verify-client.mjs:149-174` 的 `FEEDBACK_REQUIRED` 要求这类调用

> 必须给出 `{ key: …, label: … }` **作为最后一个实参**。

`runImage` / `runImages` / `runTurnVideo` / `runImageJob` / `runSequenceVideo` … 都在表里。
所以 **`model` 必须放进 payload 对象**（`runImage({ projectId, key, model })`），
**不能做成位置参数**（`runImage(payload, model, { key, label })`），否则这条契约直接挂。

### 9.2 两个会静默出问题的坑

**④ `maskConfig` 的 `...rest` 会把 `channelSecrets` 泄露给浏览器。**

`config.ts:337-338`：

```ts
export function maskConfig(config: Config): ConfigView {
  const { arkApiKey, minimaxApiKey, ...rest } = config;   // ← ...rest 会把新字段一起 spread
  return { ...rest, arkApiKeySet: …, minimaxApiKeySet: … };
}
```

`ConfigView extends Omit<Config, "arkApiKey" | "minimaxApiKey">`（`config.ts:349` 附近）。
`Config` 一加 `channelSecrets`，它就在 `Omit` 之外、被 `...rest` 整个 spread 进视图。
**必须同时改两处**：`Omit` 加上 `"channelSecrets"`，解构里也把它取出来丢掉。
方案 §3.3 写了「永不出现」，但没给机制——这是安全问题，不是风格问题。

**⑤ `normalizeConfig` 是逐字段重建，漏一个字段＝每次保存都清空它。**

`config.ts:256-279` 每一行都是 `asString(raw.x, DEFAULT_CONFIG.x)`，**没有 `...raw` 透传**。
而 `saveConfig` 每次都走它。所以新增的 `channels` / `suppliers` / `bind` / `channelSecrets` /
迁移标记，只要有一处没显式搬过去，就会**在用户下一次保存任意设置时被静默清空**。
同理，**迁移标记本身也必须被 `normalizeConfig` 搬过去**，否则它会被清掉、迁移反复执行——
而迁移的触发条件是「`channels` 为空」，用户手动删光渠道后会**凭空冒出迁移出来的渠道**。

|---|---|
| `arkApiKey` / `arkBaseUrl` / `arkModel` / `arkRedrawModel` / `arkSize` / `arkWatermark` / `arkTimeoutMs` | `bind.image.default` 指向的供应商 + 它的渠道 |
| `minimaxApiKey` / `minimaxBaseUrl` / `minimaxModel` / `minimaxDuration` / `minimaxResolution` / `minimaxPathPrefix` / `minimaxPromptOptimizer` / `minimaxTimeoutMs` | `bind.video.default` 指向的供应商 + 它的渠道 |

**两个方向的投影：**

```
F→C（写完扁平字段后）
  默认渠道 = { protocol: "ark", baseUrl: arkBaseUrl,
               models: [arkModel, arkRedrawModel?],
               options: { size: arkSize, watermark: arkWatermark, timeoutMs: arkTimeoutMs } }
  默认供应商 = { name: "默认账号", channelId: 默认渠道 }
  channelSecrets[默认供应商] = arkApiKey          // clearArkApiKey → 写空串
  ——只覆盖这一条默认渠道/供应商，**不碰用户手工建的其它渠道**

C→F（写完渠道 / 供应商后）
  两个扁平字段组 ← 上面那张表的两个默认渠道/供应商反向读回
  ——只覆盖扁平字段组，**不碰 cellWidth / rowOrder 等其它配置**
```

**触发点：**

- `saveConfig` handler（`index.ts:245-293`）写完 `patch` 后 → 跑一次 F→C；
- `saveChannel` / `deleteChannel` / `saveSupplier` / `deleteSupplier` / `bindSupplier`
  → 跑一次 C→F；
- `saveSupplierKey` → 写 `channelSecrets` **并**回写对应的那个扁平 key。

**为什么这个环是闭合的**：`deleteChannel` 已有「仍被供应商指向就拒绝」、
`deleteSupplier` 已有「仍被 `bind` 引用就拒绝」（§3.2）——所以两个默认供应商**永远删不掉**，
扁平字段永远有投影目标，环不会断。

**verify-host 要断言的不变量：**

1. 只走 `saveConfig`（旧的设置页路径）→ 渠道层的值与扁平字段一致；
2. 只走新 RPC（`saveChannel` 等）→ 扁平字段跟着变；
3. 两条路径交替走 → 仍然一致，且**没有产生重复渠道**（迁移不会二次发生，见 9.2 ⑤）；
4. 用户手工加第二条渠道后，扁平字段仍只反映**绑定的默认**那一条。

U4 删掉扁平字段时，这一节整体作废。

## 附录 A · 参考 dsh-imagegen 的结构取舍

`dsh-imagegen`（`@dickpy/dsh-imagegen`）已经把这套东西做成了产品在跑，存取两端的做法值得直接借用。
关系图见工作区 `arch/imagegen-channels.architecture.html`。下面只列**会影响我们取舍**的几条。

### A1. 它的形状

```ts
// index.ts:426-446（schemastery schema）
channels: z.array(z.object({ id, preset, name, apiUrl, apiUrlFull,
                             protocol, auth, subscription, models: [{ alias, id }] }))
channelSecrets: z.dict(z.string().role('secret'))
defaultChannelId: z.string()
defaultModel: z.string()
apiUrl / apiKey / imageModels          // 旧单端点字段，保留着做迁移
```

它自己把理由写在注释里（`index.ts:350-355`）：

> Channels own the endpoint + model catalog. The API key of each channel lives in
> `channelSecrets` (a secret dict keyed by channel id) instead of inside the channel
> objects — dsh-settings redaction supports dict/array containers, but **path ops cannot
> reach inside arrays**, so a whole-array write must never carry secrets it would clobber.

### A2. 四个需要决策的点

**① `channels` 用数组还是字典。** 它用**数组**，这正是密钥必须外置的直接原因——path op 进不了数组元素。
本方案第 2 节用的是**字典**（`channels.<id>`）。字典的好处是 `channels.<id>.<field>` 是可寻址的，
patch 不必整对象写回；代价是顺序要靠别的手段表达。

> 建议：**用字典**（我们的 patch 语义比它简单，字典能省掉一整层 op 机制），
> 但**密钥仍然单独存**——理由见 A3。

**② 密钥为什么仍要单独存（即使字典可寻址）。** 因为真正的危险不是「路径到不了」，而是
「任何一次**整对象/整数组**写回都会覆盖没重填的字段」。字典可寻址只解决了「能不能精确写」，
不解决「写错范围会不会误伤」。密钥单独一层后，渠道对象里根本不存在 secret，
`maskConfig` 也不用再维护白名单——回传浏览器天然安全。

**③ 每个渠道一个模型，还是多个模型。** 它允许 `models: [{alias, id}]`，一个渠道挂多个模型
（别名 → 上游 id）。

> **已在 7.1 ④ 定案：跟它一样，渠道带 `models: string[]`，模型使用时可选。**
> 我原先建议「先保持一渠道一模型」，被推翻了——因为 `arkRedrawModel` 这个补丁的存在本身
> 就证明「同一端点多个模型」是真实需求，而不是可以往后拖的优化。
> 差别只在于：它用 `{alias, id}` 做别名映射，我们先用纯 id 列表，够用。

**④ 绑定粒度。** 它只有 `defaultChannelId` + `defaultModel`（一个默认渠道、一个默认模型）。
我们需要更细，因为同一个能力下有**用途不同、对模型要求也不同**的四处调用（拆件摊平图 vs 原地重绘
vs 逐方向生图 vs 走三步视频）。这是我们的方案比它复杂的地方，也是必要的复杂。

注意它把「渠道」和「模型」都放在一条 bind 里（默认渠道 + 默认模型），而我们拆成了
**供应商（含渠道）+ 可选的模型**——因为我们多了一层 key 与 url 的解耦。见 7.2 第 1 条。

### A3. 可以直接照抄的两件事

**迁移做法**（`index.ts:626-644`，已验证可用）：旧字段全部保留不删；`channels` 为空时用旧字段
合成一个「默认渠道」，并把旧 `apiKey` 搬进 secrets。它连注释都写好了：
*"so upgrades never break"*。我们方案 3.4 节与此一致。

**界面如何知道「已设置」**（`routes.ts:764/800`、`477-479`、`settings-form.ts:139-149`）：
读路径一律 `describe({ redactSecrets: true })`，桥只回一个**布尔旁路** `secrets: [{ path, set }]`，
密钥字段的 `format()` 恒返回空串——所以「空草稿 = 不改」。

> 我们不必搬它的 path-based 旁路（我们的 `saveConfig` 不是通用 path-op 桥）。
> 用**每供应商**一个 `keySet` / `keyHint` 更省事，语义等价。但它那条「`format()` 恒为空串、
> 空草稿即不改」的约定值得照搬——我们现在的 `arkApiKey` 就是这个语义。

### A4. 明确**不要**照抄的部分

它的协议分派是**条件链**，不是注册表：`ChannelProtocol` 只有 `images` / `chat-completions`
两个值，DashScope / MiniMax / 智谱这些原生协议由 9 个 `ModelFamily` 在 `engine.ts:1197-1209`
的 if 链里隐式选中，再被 `apiUrlFull` 与 `chat-completions` 优先短路。
结果是「新增一个原生协议要改 6 处、新增一个订阅 vendor 要改 8 处」。

我们的 engine 已经有 `ImageInstance` / `VideoInstance` 接口 + `registry.ts` 注册表，
新增厂商是「写一个实例 + 登记一行」。这是我们已经比它好的地方，**别为了对齐而退回条件链**。

### A5. 它的两根**正交**轴（本文档最容易讲错的地方）

读它的代码时很容易把两件事混成一件——我自己在早期稿子里就搞反过层级。它们**正交**，
且**传输优先**：

| 轴 | 字段 | 值 | 挂在哪 | 谁决定 |
|---|---|---|---|---|
| **传输** | `channel.protocol` | `auto` / `images` / `chat-completions` | 渠道 | 用户配置；`auto` 时按 URL 猜——`isChatCompletionsUrl()` 看 pathname 是否以 `/chat/completions` 结尾 |
| **协议** | `ModelFamily` | 9 类 | **模型** | `describeModel()` 按模型 id 正则推 |

`generateImage()` 的顺序（`engine.ts:1193-1216`）：

1. 传输是 `chat-completions` → 走聊天接口生图，**到此结束**（完全不看协议）；
2. 否则、且 `apiUrlFull !== true` → 按协议（模型族）挑**原生端点**：qwen / minimax / zhipu；
3. 否则 → **`requestOneImage()`**，通用入口。

外加一个逃生舱 `apiUrlFull: true`：**「我给了完整 URL，你别按协议猜、也别再拼路径」**。

**协议在哪里被真正用掉：`requestOneImage()` 内部（`engine.ts:735-820`）。**

这是整份文档最关键的一处证据。它是**一个函数**，鉴权头在最前面统一构造（`742-744`
的 `authorization: Bearer …`），然后**并排四个协议分支**，判断依据全是 **`params.model`**：

| 分支 | 判断 | 请求体 |
|---|---|---|
| grok | `isGrokImagine(params.model)` | JSON，`image: { url, type }` + `aspect_ratio` |
| nanobanana | `isNanoBanana(params.model)` | multipart + `aspect_ratio` / `image_size` |
| seedream | `isSeedream(params.model)` | JSON，`image` 数组；**内部还有子分支** `isVolcSeedream(...) ? 'url' : 'b64_json'` |
| 兜底 | 其它 | 通用 OpenAI multipart |

**三个值得记住的点：**

- **协议不是渠道字段，而是随调用走的**——判断依据是 `params.model`，也就是这次调用的模型。
  所以它天然属于「这次调用」的上下文。
- **同一个协议内部还有方言**（火山 seedream 用 `url`、别家用 `b64_json`）。这说明
  「一协议一个适配器」会越拆越细，而真正共享的那部分（鉴权、参考图解码、大小上限、
  响应解析）留在外面——**粒度应该按共享边界划，不是按协议划**。
- **`unknown` 家族的界面标签就叫「未知协议」**（`model-catalog.ts:135`）。
  也就是说「协议」这个词在它的**用户界面**里，指的就是这一层，而不是 `channel.protocol`
  那个传输开关。命名上我们跟随用户可见的那一侧。

**我们对它的两处改动：**

- 协议**由模型 id 正则猜** → 我们改成**在渠道上显式选一次**（`channel.protocol`），去掉猜的
  环节。这是改进，不是偏差：代价是用户建渠道时多选一下，好处是①未知模型不会被静默按
  通用协议发出去，②新增原生协议不再需要动正则表。
  （**不**逐模型配——协议是「这个端点怎么说话」，一个端点一种说法；理由见 §2 与 §7.1⑥。）
- 它的协议与传输两根轴，我们**只保留协议**（见 §7.1⑥）。传输轴的存在是 if 链的产物，
  我们换成适配器 + 注册表之后就不需要了——真要做聊天接口生图，再写一个适配器即可。
